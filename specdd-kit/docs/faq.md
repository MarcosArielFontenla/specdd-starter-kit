# FAQ

## Secrets

**Does the wizard ever write real secrets into the ZIP?**
No. The wizard's MCP step writes `.vscode/mcp.json` with **input variable
placeholders** (e.g. `${input:github_pat}`, `${input:sonar_token}`,
`${input:sonar_host}`, `${input:pg_connection_string}`, `${input:figma_key}`), not
literal tokens. VS Code prompts you for these values when the server starts and
stores them using its own secret input mechanism — they are never written to a
file in your repo.

**Where should I actually put tokens, then?**
In VS Code's MCP input prompts when asked, or in your shell/CI environment
variables. Never paste a token directly into `.vscode/mcp.json`,
`context/*.md`, or a spec — the project constitution generated by this kit
explicitly forbids secrets in specs, code, or examples, and `context/tech-stack.md`
/ specs are meant to be shared and reviewed freely.

**What if I accidentally commit a secret?**
Rotate it immediately at the provider, then remove it from history using your
normal git hygiene process. This kit doesn't include secret-scanning tooling
itself — pair it with your organization's existing pre-commit/CI secret scanning
if you have one.

## MCP

**Do I need MCP servers to use this kit?**
No. The entire constitution → specify → plan → tasks → implement loop works with
zero MCP servers configured. MCP just gives your agent extra tools (reading GitHub
issues, querying a database, driving a browser, etc.) when you want them.

**Which MCP servers does the wizard support?**
`github`, `sonarqube`, `context7`, `postgresql`, `playwright`, and `figma` today.
Select only the ones you'll actually use — see `SETUP.md` § 4 for setup steps and
`.github/instructions/mcp-tools.instructions.md` for the usage guardrails every
agent in this kit follows.

**Can I add an MCP server the wizard doesn't offer?**
Yes — `.vscode/mcp.json` is a standard VS Code MCP config file; add entries by
hand following the same shape the wizard generates. The guardrail in
`mcp-tools.instructions.md` still applies: don't add servers without confirming
with the team, since each one expands what an agent can do on your machine.

## Which agent should I use?

**Does this kit require GitHub Copilot?**
No. `.github/prompts/*.prompt.md`, `.github/instructions/*.instructions.md`, and
`.github/agents/*.agent.md` are plain Markdown with light frontmatter — GitHub
Copilot auto-loads them from `.github/`, but Claude Code, Cursor, and Gemini can
all read and follow the same files. The wizard's **Agent & LLM** step just records
which agent/model you're primarily using, so the generated
`.github/copilot-instructions.md` names it explicitly; it doesn't gate which agent
is technically allowed to use the rest of the scaffold.

**What if my team uses more than one agent?**
That's the expected case, not an edge case. Keep the prompts and instructions as
they are — they're written to be agent-neutral — and let each engineer use
whichever agent they prefer. The spec/plan/tasks artifacts in `specs/` are the
shared source of truth regardless of which agent produced or reads them.

## Offline / air-gapped use

**Does the wizard need internet access?**
Only for `npm install` (first time) and to install MCP server packages you select
(they're fetched via `npx` on first run). Once dependencies are installed, running
the wizard itself (`npm run dev`) and using the generated prompts/instructions
inside your coding agent works offline, modulo whatever network access your agent
itself needs to reach its model.

**Can I use the generated scaffold without ever running an AI agent?**
Yes. `context/`, `specs/`, and `templates/` are plain Markdown meant to be read and
written by humans too — the `/specdd-*` prompts are a convenience for agent-driven
workflows, not a requirement. You can write `spec.md`/`plan.md`/`tasks.md` by hand
from the templates in `templates/` and still get the review-before-code benefit of
SDD.

## Other

**Is there governance tiering (L1–L4) in this kit?**
No. This kit uses one flat constitution and one flow for every project, regardless
of size or maturity. See `docs/specdd-methodology.md` for what's intentionally out
of scope.

**Does this kit deploy anything or integrate with Azure DevOps?**
No. It scaffolds specs, prompts, and instructions only. Issue-generation prompts
(`/specdd-issues-from-*`) produce plain text you paste into whatever tracker your
team already uses.

**What's `specforge-kit`?**
A planned future kit (role-based scaffolds for BA/QA/Dev/UX) — not implemented in
this repository yet. Don't expect its files or commands to exist today.
