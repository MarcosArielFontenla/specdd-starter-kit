# Project Context

> Part of the Spec-Driven Development flow: constitution → specify → plan → tasks → implement.

## Purpose
Describe what this project is, who it serves, and why it exists, so every spec written afterward starts from shared understanding.

## Inputs
- Project name and one-line mission
- Primary users / personas
- Current stage (greenfield, active development, maintenance)

## Content

### Project name
SPECDDSTARTERKIT — example project

### Mission
A short statement of what this product does and for whom. Example: "Give small teams a Copilot-ready Spec-Driven Development scaffold in under two minutes."

### Users & personas
- **Primary persona:** the developer running the wizard to bootstrap a new repo.
- **Secondary persona:** a teammate joining later who reads `specs/` to understand intent.

### Current stage
Greenfield — no production users yet; early iteration.

### Repositories / systems in scope
- List the repos, services, or packages this project context applies to.

### Non-goals
- Things intentionally out of scope for this project (kept short — link to specs for detail).

## Definition of Done
- [ ] Mission statement is one or two sentences and unambiguous
- [ ] Primary and secondary personas are named
- [ ] Current stage reflects reality (update as the project matures)
